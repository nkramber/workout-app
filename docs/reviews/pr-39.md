### P2-2: Another tab can restore history after deletion

Status: fixed in `e0a01c9b560980b6c6a6cf8dea18432302406fb7`.

Open at: `6beaab0f643529e75d2de435d97f53c91f824c36`.

File: `web/src/lib/history.ts:43-50`.

Trigger: Keep a second app tab open with a workout or set in its outbox. Let that tab send `SyncOutbox`, then let the owner delete history from the first tab before the second request finishes applying its entry.

Expected: D-314 and D-315 require the deletion to remove the owner's workout history from the server and phone. A completed delete must not allow a pending sync to recreate that history.

Actual: `deleteAllData` waits for `deps.sync`, which calls the one `SyncEngine` instance in the current tab. Each tab has its own engine. A second tab can therefore have a `SyncOutbox` request in flight while the first tab deletes its local IndexedDB records and calls `DeleteHistory`. `DeleteAll` removes the server workouts and op ids. `SyncOutbox` has no deletion fence, so its later write can recreate a workout after the delete. The second sync in the first tab does not coordinate with the second tab.

Consequence: The UI reports that deletion passed while a stale request can restore workout history on the server.

Correction: Coordinate deletion with every sync that can write for this uid, or add a server-side deletion generation that rejects pre-deletion outbox entries.

Regression check: `make go-test` and `make emulator-test` passed on `e0a01c9b560980b6c6a6cf8dea18432302406fb7`. `TestMemoryDeleteAll`, `TestFirestoreDeleteAll`, and `TestSyncAfterDeletion` reject an entry dated before the deletion.

### P2-3: A phone clock ahead can bypass the deletion fence

Status: fixed in `4cd1bd51bb36d59b07a2f03e31782abcc5e379dc`.

Open at: `e0a01c9b560980b6c6a6cf8dea18432302406fb7`.

File: `go/internal/workout/store.go:561-562` at the earlier head.

Trigger: The phone clock runs ahead of the API clock. The phone queues an entry before deletion, but its `Entry.At` is later than the server deletion time.

Expected: D-315 requires deletion to stop old history after a completed delete.

Actual at the earlier head: `DeleteAll` recorded `s.now()` on the API. `Apply` compared that value with `e.At`, which the phone supplied. The stale entry passed when its timestamp was later. The current store compares server generations.

Consequence: A supported clock difference let a stale outbox entry restore deleted workout history.

Correction: The author replaced the phone time with a server-controlled history generation.

Regression check: `make go-test` and `make emulator-test` passed. `TestMemoryDeleteAll` and `TestFirestoreDeleteAll` reject an old-generation header with a phone time 24 hours later. They accept a header with the new generation.

### P2-4: A plan request can save after history deletion

Status: open.

Open at: `4cd1bd51bb36d59b07a2f03e31782abcc5e379dc`.

Files: `go/internal/usersvc/usersvc.go:93-98`, `go/internal/plan/make.go:148-163`, and `go/internal/plan/store.go:203-224`.

Trigger: Start `RequestPlan` and let it reach its AI call. Complete `DeleteHistory` while the plan request waits. Then let the plan request finish.

Expected: D-315 requires the deletion to remove the plan. When `DeleteHistory` reports success, the server must not hold a plan from a request that started before the deletion.

Actual: `DeleteHistory` deletes the plan. The in-flight `Maker.Make` then calls `Plans.Save`. The Firestore transaction reads only the exclusions document, then writes the plan. It does not read a deletion generation or the plan document, so the delete does not conflict with the save.

Consequence: The deletion call can report success while a new plan appears on the server and on the phone. The acceptance story fails.

Correction: Fence plan saves against the history deletion generation. Make the generation check and plan write atomic with deletion, or use an equivalent server-side fence.

Regression check: Add an emulator test that pauses a plan request before `Save`, completes `DeleteHistory`, then releases the request. The request must not leave a plan. No such check exists at this head.
