## Findings

### P2-1: A failed sync does not stop a plan request

Status: open.

Open at: `e2721cd532d7747708118802eff71aff51133e30`.

File: `web/src/lib/plan-api.ts:63-64`.

Trigger: An inventory entry waits in the outbox. `SyncOutbox` fails, but the later `RequestPlan` call succeeds.

Expected: Apply the pending inventory changes before a plan request. A plan reads confirmed machines alone (D-193), and inventory changes use `SyncOutbox` (D-272).

Actual: `SyncEngine.syncNow` records a failure and resolves without an error. `requestPlan` then calls the plan service even when the inventory entry remains in the outbox.

Consequence: The server can build a plan from its old inventory. The plan can omit a machine that the phone shows as confirmed, or use equipment that the phone removed.

Correction: Make the plan request stop when the sync fails or inventory entries remain pending. Show the sync failure to the owner.

Regression check: Add a test with a pending inventory entry and a failing `SyncOutbox` call. Verify that `RequestPlan` does not start and that the screen shows the failure.
