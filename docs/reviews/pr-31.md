## Findings

### P2-1: Distance input exceeds the `int32` contract

Status: open.

Open at: `1ef826cfd47fe691434be7048aa47a4f573e493d`.

File: `web/src/lib/workout.ts:364-369`.

Trigger: Enter `214748364.8` miles. The parser accepts the text and returns `2147483648` tenths.

Expected: D-165 and `proto/workoutapp/v1/workout_service.proto` require a nonnegative value in an optional `int32` field.

Actual: `parseMiles` accepts the value. The cardio form does not mark it invalid, so it saves an out-of-range value in the local record and outbox payload.

Consequence: The queued cardio entry does not fit the API contract and can not sync as a valid `CardioEntry`.

Correction: Reject a parsed distance above `2147483647` tenths. Test the largest valid value and the next value.

Regression check: Add parser and form tests for `214748364.7` and `214748364.8`. No regression test exists at this head.

### P2-2: A released wake lock leaves the screen state stale

Status: open.

Open at: `1ef826cfd47fe691434be7048aa47a4f573e493d`.

File: `web/src/lib/wake-lock.ts:31-44`.

Trigger: The browser releases the wake-lock sentinel while the app remains visible.

Expected: D-265 requires the app to show a notice when the phone refuses the lock. The workout screen must not report an active lock after the browser releases it.

Actual: The code never subscribes to the sentinel's `release` event. The state remains `on`, and the app does not request another lock until a visibility change.

Consequence: The screen can turn off during a workout while the owner sees no notice.

Correction: Handle the sentinel's `release` event and update the state or request a new lock. Add a test for a release while visible.

Regression check: Add a wake-lock test that releases the sentinel while visible and checks the state and next request. No regression test exists at this head.
