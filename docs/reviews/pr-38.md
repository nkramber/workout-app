## Findings

### P2-1: New plans lose exercise history beyond the 100-workout window

Status: open.

Open at: `99e984dd3eb23a440b614091c31328c3c6953f8c`.

File: `go/internal/revise/revise.go:289-301`.

Trigger: The owner has more than 100 newer finished workouts that omit one exercise. An older workout has its target copy for that exercise.

Expected: D-301 says an exercise with history gets no calibration in a new plan. D-179 also requires a 70 percent return load after a gap of 91 days or more.

Actual: `History` calls `finished`, which caps the input at the newest 100 workouts. It builds each exercise history only from that truncated list. `plan.Request` then gives an empty history to the policy for an omitted exercise, which treats it as new and marks its first set for calibration.

Consequence: A returning exercise can lose its prior working load and start from the estimate at 100 percent. This can bypass the lower return load and recalibrate an exercise that has history.

Correction: Keep the latest target copy and outcome for each exercise. A per-exercise history query can show when its result is complete. Add a test with more than 100 newer workouts that omit one exercise. Verify that the return target uses the older logged outcome.

Regression check: No test covers this boundary at this head. Add the case above, then run `make go-test` and the API history acceptance test.
