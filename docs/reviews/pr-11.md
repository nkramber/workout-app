## Findings

### P2-1: The deploy guard leaves a check-to-deploy race

Status: open.

Open at: `e5f724b24cfbcbaf24de3a78219bbdac2aaf74e9`, `5f9d991e16e564551b156865044ecd630627a379`.

File: `cloudbuild/api.yaml:32-55`.

Trigger: an older build passes `guard`. A newer merge then starts and completes its deploy before the older build reaches its `deploy` step.

Expected: the deployed API, web app, and rules must not move back to an older commit after a newer merge (D-14, D-18).

Actual: `deploy_order.py` checks `main` before the deploy step. It does not hold a lock or recheck atomically with the deploy. The newer build can pass its own guard and deploy. The older build can then deploy its image. The same gap exists in the web and rules builds.

Consequence: a valid build ordering can leave an older API, web app, or ruleset live after the newer build succeeds. The later version check can fail, but it does not restore the newer deployment.

Correction: serialize the guard and deploy for each target as one critical section. Or make the target reject an older commit. Apply the correction to all three targets.

Regression check: pause an older build after its guard. Merge and deploy a newer change to the same target, then resume the older build. Verify that the older build cannot change the live version.
