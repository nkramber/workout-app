## Findings

### P2-1: An older build can replace a newer deploy

Status: open.

Open at: `e5f724b24cfbcbaf24de3a78219bbdac2aaf74e9`.

File: `cloudbuild/api.yaml:30-39`.

Trigger: two merges change paths watched by a deploy trigger. The newer build deploys first. Then the older build deploys its image.

Expected: the live API, web app, and rules must not move back to an older commit after a newer merge (D-14, D-18).

Actual: each trigger deploys its own commit. It does not check whether that commit remains current on `main`. The check detects an old commit only after deployment. `docs/deploy-and-rollback.md:24` confirms that this race can leave the old version live and requires a manual redeploy.

Consequence: the deployed app can revert after a newer merge. A failed build check does not restore the newer release.

Correction: add serialization to each deploy stream or verify that the commit is current on `main` before release. Apply the guard to the API, web, and rules triggers.

Regression check: model two builds that finish out of order. Verify that the older build can not change the live version after the newer build deploys.
