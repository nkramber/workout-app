## Findings

### P2-1: An older build can replace a newer deploy

Status: fixed in `9ec3819f10addc1edacbbe03dd507d7a63e59175`.

Open at: `e5f724b24cfbcbaf24de3a78219bbdac2aaf74e9`, `5f9d991e16e564551b156865044ecd630627a379`.

File: `cloudbuild/api.yaml:35-57`.

Trigger: an older build passes its deploy guard. A newer build then deploys before the older build reaches its separate deploy step.

Expected: an older commit must not replace a newer deploy (D-14, D-18).

Actual: at the two earlier heads, the old build deployed after the new build.

Consequence: the API, web app, or rules can move back to an older commit.

Correction: each build now holds a part-specific Cloud Storage lock while it reads `main` and runs its deploy command.

Regression check: `make verify` passed at `9ec3819`. The `TwoBuilds.test_an_older_build_paused_after_its_guard_can_not_move_the_part_back` test passed. It pauses the older build in its deploy command, starts the newer build, and proves the newer deploy runs last. The control with no lock fails the ordering assertion.

### P2-2: A slow history read can outlive the stale-lock limit

Status: fixed in `360f1dbcd07da714e605e6445242179fafce658e`.

Open at: `9ec3819f10addc1edacbbe03dd507d7a63e59175`.

File: `docs/tools/deploy_order.py:52-55, 76-82, 167-189`, `cloudbuild/api.yaml:35-57`.

Trigger: a build holds its lock while `read_main` clones `main`. The fetch takes more than 20 minutes, or it takes long enough that a later deploy crosses the 20-minute lock age. A newer build then treats the live lock as stale, removes it, and deploys. The older build can finish its earlier history read and deploy after the newer build.

Expected: only one build of a part can hold its lock until that build stops. An older deploy must not replace a newer deploy (D-14, D-18, D-143).

Actual: `STALE` is 20 minutes. The clone in `read_main` has no timeout. Only the deploy subprocess has a 10-minute timeout, while the Cloud Build deploy step can run for 30 minutes.

Consequence: a slow but live build can lose its lock and deploy at the same time as a newer build. This restores the ordering fault that P2-1 addresses.

Correction: set a five-minute timeout for the full read of `main`, a ten-minute timeout for the deploy command, and a twenty-minute stale limit. Set each deploy step timeout to forty minutes.

Regression check: `make verify` passed at `360f1db`. `Bounds.test_a_read_past_its_limit_deploys_nothing_and_frees_the_lock` proves that a late read makes no deploy and releases the lock. `Bounds.test_read_main_stops_at_its_timeout` proves that the clone and both Git calls get the remaining read deadline. `test_the_read_and_the_deploy_get_their_limits` and the deploy-config test prove the limits and the Cloud Build step budget.
